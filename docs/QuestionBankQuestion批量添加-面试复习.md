# QuestionBankQuestion 批量添加逻辑面试复习

本文聚焦代码：`src/main/java/com/fu/interview_copilot/service/impl/QuestionBankQuestionServiceImpl.java` 的 `QuestionBatchAddToQuestionBank` 与 `batchAddQuestionsToBankInner`（108-192 行）。

目标：把这段代码讲成“可落地 + 可权衡 + 可优化”的工程案例。

---

## 1. 这段代码在做什么

主流程可拆成 6 步：

1. 参数与题库存在性校验  
2. 查询有效题目 id（过滤掉不存在题目）  
3. 查询已在题库中的题目（去重）  
4. 计算真正需要插入的 `insertQuestionIds`  
5. 按批次异步执行 `saveBatch`（`CompletableFuture + 自定义线程池`）  
6. 等待所有任务完成并关闭线程池

事务写入在 `batchAddQuestionsToBankInner` 中，用 `@Transactional` 包裹，并捕获数据库异常映射为业务异常。

---

## 2. 面试怎么讲“为什么这样设计”

可以用一句总述：

> 这是一个“先做集合差集去重，再做并发批写”的批量入库策略，目标是在保证幂等和错误可解释的前提下提升吞吐。

然后展开这 4 个关键点。

---

## 3. 线程池选择与参数解释（重点）

代码里线程池参数：

- `corePoolSize = 20`
- `maximumPoolSize = 50`
- `keepAliveTime = 60s`
- `workQueue = LinkedBlockingQueue<>(10000)`
- `RejectedExecutionHandler = CallerRunsPolicy`

### 3.1 为什么说是 IO 密集型

任务本质是数据库写入，瓶颈更偏 IO（网络、DB 连接、磁盘刷盘），不是纯 CPU 计算。  
IO 密集型一般线程数可高于 CPU 核数，所以会看到 20~50 这种配置。

### 3.2 每个参数的面试答法

- `corePoolSize`：常驻线程，平时就保留；避免频繁创建销毁线程。
- `maximumPoolSize`：突发流量上限，超出核心线程并且队列满时才会扩容到这个值。
- `queue(10000)`：任务缓冲区，大队列可以抗尖峰，但也会拉高内存占用和任务等待时延。
- `CallerRunsPolicy`：拒绝时由提交线程执行任务，等价于“反压”，防止任务无声丢失。

### 3.3 这组参数的潜在问题（要会自我批判）

1. 队列很大 + 拒绝策略触发晚：更容易“堆积慢”，不容易及时暴露系统过载。  
2. 没有按 DB 连接池上限反推并发：线程多不代表吞吐高，可能只会让连接争抢更严重。  
3. 每次调用都 new 线程池并 shutdown：生命周期短，创建销毁有开销，不如复用全局线程池 Bean。

面试加分说法：

> 生产会把线程池托管成 Spring Bean，参数按数据库连接池上限与压测结果调优，而不是在业务方法里临时创建。

## 4. 为什么要“起代理”（`AopContext.currentProxy()`）

这段代码在循环里拿当前代理对象再调用 `batchAddQuestionsToBankInner`，核心目的：

- 让 `@Transactional` 生效。

### 原理（必会）

Spring 事务是 AOP 代理实现的。  
同类内部 `this.xxx()` 属于“自调用”，不会经过代理，事务注解可能失效。  
通过代理对象调用，才会进入事务拦截器。

### 面试标准表达

> 我把事务方法拆出来，并通过代理调用，避免 self-invocation 导致事务失效。

### 也要知道的替代方案

1. 把事务方法下沉到另一个 `Service`，由外部 bean 调用（最清晰）。
2. 用 `TransactionTemplate` 显式事务（可读性稍差但可控）。
3. 保留 `AopContext.currentProxy()` 但要确认开启了 `exposeProxy=true`，否则可能报错。

---

## 5. 为什么批处理 + `CompletableFuture`

### 5.1 批处理的价值

批处理本质是减少“每条记录一次往返”的开销。  
在这里虽然 `batchSize = 1`（实际上没有形成真正 batch），但结构已经具备扩展到 `50/100/200` 的能力。

### 5.2 `CompletableFuture` 的价值

- 易于表达“并行发任务 + 汇总等待”；
- `allOf(...).join()` 一处等待全部完成；
- 相比手写 `CountDownLatch` 更函数式。

### 5.3 当前实现的风险点（面试可讲优化）

1. `join()` 会把异常包在 `CompletionException`，当前代码未统一拆包处理，调用层感知较弱。  
2. 并发写同一题库，可能增加唯一键冲突概率（虽然有异常兜底）。  
3. `batchSize=1` 导致任务过细，线程调度开销大，吞吐不一定优。

---

## 6. 幂等性与一致性怎么回答

这段代码有两层幂等保护：

1. 业务层先查已存在关联，做差集后只插入新增项；  
2. 数据库层有唯一键（`questionBankId + questionId`），最终兜底防重复。

面试可这样讲：

> 我做了“业务去重 + 数据库唯一约束”的双保险，业务层减少异常，数据库层保证最终一致。

## 7. 你可以主动提的优化建议（高频追问）

### 优化 1：把线程池改为全局复用

- 现在方法内创建线程池，建议改成 Spring 配置的 `ThreadPoolTaskExecutor`。

### 优化 2：把 `batchSize` 调到合理值

- 例如 50/100，根据 SQL 包大小、连接池、锁等待压测确定。

### 优化 3：补充参数健壮性校验

- 当前 `validQuestionIds == null` 的判断意义不大，列表通常不会是 null，而是 empty。  
- 应改为 `CollUtil.isEmpty(validQuestionIds)`。

### 优化 4：异常聚合与部分失败策略

- 当前是一锅端语义；可明确是“全成功/部分成功/失败重试”哪一种。

### 优化 5：减少不必要并发

- 如果批量规模小（如 <200），串行 `saveBatch` 可能更简单且够快。  
- 并发不是越多越好，关键看 DB 能否承接。

## 8. 可直接背的面试答案模板

### Q1：为什么用线程池而不是直接 for 循环？

> 批量入库是 IO 密集操作，适度并发可以提高吞吐，且通过有界队列和拒绝策略保证系统不过载；不过并发参数要结合数据库连接池压测，不是越大越好。

### Q2：为什么要通过代理调用事务方法？

> Spring 事务基于 AOP 代理，同类内部自调用不会触发事务拦截，所以我通过代理对象调用 `@Transactional` 方法来保证事务生效。

### Q3：`CompletableFuture.allOf().join()` 的好处和坑？

> 好处是并发编排清晰、统一等待点；坑是异常被包装，需要统一拆包处理并落地可观测日志。

### Q4：怎么保证不重复添加题目到题库？

> 先查差集再插入减少冲突，再用数据库唯一键兜底保证强约束，出现冲突转业务异常给前端明确提示。
