# 08 - 缓存一致性与分布式锁

---

## 1. 什么叫缓存一致性

**MySQL 里的数据** 和 **Redis 里的副本** 是否一致。

本项目目标：**最终一致**即可（题目改完几秒内读到新版可以接受），不要求强一致。

---

## 2. 读写策略选型

| 策略 | 做法 | 本项目 |
|------|------|--------|
| 先删缓存，再写 DB | 可能删完后、写 DB 前，别人又把旧数据写入缓存 | 不推荐单独使用 |
| **先写 DB，再删缓存** | 主流 | ✅ 采用 |
| 先写 DB，再更新缓存 | 要写完整 JSON，易漏字段 | 不用 |
| 延迟双删 | 写 DB 前后各删一次缓存 | 进阶可选 |

---

## 3. 先写 DB 再删缓存 — 时序分析

```
正确主流程：
  T1: UPDATE question SET content=新 WHERE id=2
  T2: DEL question:detail:2
  T3: 用户读 → miss → SELECT 新数据 → SET Redis
```

### 3.1 仍可能出现的短暂问题

```
线程1: UPDATE DB（事务未提交）
线程2: GET miss → SELECT 到旧数据？→ SET 旧数据到 Redis
线程1: 提交事务
线程1: DEL Redis
```

线程2 若在提交前读到旧数据并写入缓存，线程1 DEL 可纠正；  
若 DEL 在 SELECT 之前、SET 在 DEL 之后，会短暂脏读 → **延迟双删**或 **事务提交后再 evict** 缓解。

### 3.2 事务提交后 evict（推荐 Phase 2）

```java
// 发布事件
applicationEventPublisher.publishEvent(new QuestionUpdatedEvent(questionId));

// 监听器
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handle(QuestionUpdatedEvent e) {
    questionCacheService.evict(e.getQuestionId());
}
```

---

## 4. 延迟双删（面试能说即可）

```
1. DEL cache
2. UPDATE DB
3. sleep 500ms（或发延迟 MQ）
4. DEL cache again
```

**为什么 sleep**：挡住「读请求在步骤 2 期间把旧值写回缓存」的窗口。

题目更新 QPS 低，本项目 **Phase 1 不必上**，面试作为演进方案。

## 5. 分布式锁解决击穿

### 5.1 问题回顾

热 key `question:detail:2` 过期 → 500 线程同时 `getById(2)`。

### 5.2 Redisson 互斥锁

锁 key：`lock:question:detail:{id}`，与数据 key 分开。

在 `QuestionCacheServiceImpl.getFromCache` 的 miss 分支：

```java
String lockKey = "lock:question:detail:" + questionId;
RLock lock = redissonClient.getLock(lockKey);
boolean locked = false;
try {
    locked = lock.tryLock(3, 10, TimeUnit.SECONDS);
    if (!locked) {
        // 未拿到锁：短暂等待后重试读缓存，或直接查 DB（简化）
        String retry = bucket.get();
        if (StrUtil.isNotBlank(retry) && !PLACEHOLDER.equals(retry)) {
            return JSONUtil.toBean(retry, Question.class);
        }
        return loader.load(questionId);
    }
    // 双重检查
    String json = bucket.get();
    if (StrUtil.isNotBlank(json) && !PLACEHOLDER.equals(json)) {
        return JSONUtil.toBean(json, Question.class);
    }
    Question question = loader.load(questionId);
    // ... 回填缓存（同前）...
    return question;
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return loader.load(questionId);
} finally {
    if (locked && lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

### 5.3 双重检查原因

拿锁期间，前一个线程可能已回填缓存，避免重复查 DB。

### 5.4 何时启用

| 场景 | 建议 |
|------|------|
| 本地开发 / 面试 Demo | 可不加锁，TTL 抖动够用 |
| 压测热 key 明显 | 加锁 |
| 面试深入问击穿 | 必须能讲锁流程 |

可加配置 `cache.question.mutex-enabled=true` 控制。

## 6. Redis 与 ES 的一致性（扩展）

| 存储 | 用途 | 一致性 |
|------|------|--------|
| MySQL | 权威 | - |
| Redis | 详情读 | 写后删缓存 |
| ES | 搜索 | 定时增量同步 |

改题后：Redis 立刻 evict；ES 可能 1 分钟内才更新 — **搜索与详情短暂不一致可接受**。
